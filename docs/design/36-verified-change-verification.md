## 3. 구현·출시 단계의 조건

각 단계는 해당 기능의 실제 실행 결과와 기존 시험·정적 분석·패키지·브라우저 검사를 함께 확인해야 한다. 현행 타입 오류와 브라우저 시험 실패가 그대로라면 새 구현의 완료 또는 정상 출시를 선언하지 않는다. [기준 기록](reviews/2026-10-14-baseline.json).

| D3 | VCT-05·07·11·12·14·23~25의 실제 수정·반영·MCP 검사 | 미실행 |

계약 예시와 문서 검사기는 구현 준비의 도구다. 실제 OS 격리·전원 중단·모델 품질·제품 효과의 시험으로 계산하지 않는다. 지원 OS와 파일 공간별 실행 증거가 없으면 지원·복구 보장의 범위를 확대하지 않는다.

## 4. 비교 설계와 중단 조건

초기 탐색은 실제 React·TypeScript 저장소 3개 이상에서 대표 변경·알려진 결함·정상 변경을 함께 비교한다. 모델·저장소·도구·제한·기준 준비를 고정한다. 기본 대안은 사용자가 이미 사용하는 코드 도구+Playwright이며, 비교 가능한 작업에서는 기존 저장소를 지원하는 생성 제품·품질 제품도 포함한다. 경쟁 제품의 공식 설명은 실행 측정 결과로 사용하지 않는다.

탐색 자료로 제품을 개선한 다음 별도 과제·저장소·평가자를 확보한다. 최종 평가의 과제·실패 판정·자원 제한·비교 기준을 실행 전에 고정한다. 반복 시행은 같은 과제에 종속되므로 독립 표본 수로 합산하지 않는다. 최종 평가 중 발견한 과제를 제품에 반영하면 해당 평가를 개선 자료로 분류하고 새 평가를 준비한다.

비교에서는 설치·기준 승인·실행·검토·수정·재시도·환경 실패와 비용을 포함한다. 사람의 직접 작업 시간과 총 완료 시간을 구분하고 동시 작업은 별도 기록한다. 성공 사례만 보고하지 않는다. 잘못된 통과는 독립 평가자가 결함을 확인했는데 도구가 ready인 경우, 잘못된 실패는 독립 기준에서 정상인데 필수 실패로 판정한 경우로 정의한다. 기존 기능 훼손은 변경 전 통과한 보존 요구의 독립 확인 실패다.

초기 제품 판단 목표는 직접 작업 시간 중앙값 30% 감소와 잘못된 통과·기능 훼손 증가 없음이다. 표본 수와 신뢰 구간은 탐색의 분산·실패율과 요구 위험에 따라 최종 평가 전에 정한다. 저장소 3개와 30%라는 수치만으로 통계적 우위를 확정하지 않는다. 정상·결함 과제를 분리해 정확한 분모와 원자료를 공개하며 과제 단위로 불확실성을 계산한다.

반복 사용은 외부 개발자가 다음 실제 작업에서 도구를 다시 선택했는지 측정한다. 별점·설치·설문 선호를 반복 사용으로 계산하지 않는다. 사용자 모집·인터뷰·공개 비교·배포는 이번 문서 작업에 포함하지 않는다.

다음 조건이면 범위 확대를 중지한다: 설정·검토 부담이 늘고 효과가 없음, 잘못된 통과 증가, 필수 기준 수정으로 성능을 개선함, 격리 도입 비용이 효과를 상쇄함, 다음 작업에서 재사용하지 않음. 이 경우 관련 실패를 분석하고 대상 작업 또는 제품 가설을 다시 판단한다.

## 5. 문서 검사 결과와 한계

문서 검사기는 JSON Schema의 내부 참조·필드표·예시·관계·판정 경계·VCR/VCT 추적·로컬 문서 링크를 확인한다. 좋은 예시뿐 아니라 필수 누락·알 수 없는 필드·고아 참조·기준 실패·회차 불일치·미정 비용·상한 초과 등의 거부 예시를 포함한다.

검사 결과는 [문서 검사 기록](reviews/2026-10-14-document-validation.json)에 저장한다. 출력의 `implementation_evidence`와 `product_effect_evidence`는 0이며, 통과 수를 제품 품질 점수로 사용하지 않는다. 3심 최종 검토가 확인한 파일 해시와 검사 이후 변경을 구분해 보관한다.
