조회일: **2026-10-14 KST**. 담당: 공식 일차 자료 조사와 설계 전 분석의 독립 검토. 이 문서는 앞으로 구현할 계약의 근거이며 구현 완료·제품 출시·표준 인증의 증거가 아니다. 공식 문서의 기능 설명, 현재 소스의 정적 확인, 설계에서 제안하는 계약을 구분한다. 브라우저·컨테이너·모델 호출은 실행하지 않았다.

### 파일 저장 대안의 구체 도입 조건

다음은 S08~S17에 따른 제안이다. 논리 테이블과 필드는 실제 DB 도입을 의미하지 않는다.

- 사례의 확정 입력과 실행 결과를 구분한다. run별 산출물은 고유 위치에 저장하고, 해시·크기·필수 자료 목록을 확인한 manifest를 마지막에 공개한다. 완성되지 않은 run은 ‘최신 성공’이나 반영 대상으로 조회하지 않는다.
- 동일 사례의 상태 변경은 작성자 하나가 책임진다. `case_id`, `run_id`, `case_revision`, `expected_revision`, `writer_id`, `manifest_digest`를 명세한다. revision 불일치는 새 작업을 자동 생성하는 이유가 아니라 현재 자료 재확인을 요구하는 오류다.
- 원본 반영의 사본과 단일 기록은 대상 쓰기 전에 내구성을 확보한다. `apply_id`, `operation_kind`, `expected_exists`, `expected_file_type`, `before_digest`, `after_digest`, `backup_path`, `state`, `last_verified_at`를 기록한다. 사후 해시를 모두 확인한 시점에만 반영 완료를 표시한다.
- 중단 복구는 각 대상이 원래 값·예정된 새 값·그 외 값 중 어디에 해당하는지 확인한다. 그 외 값은 사용자 또는 외부 변경으로 간주해 자동 덮어쓰기를 금지한다. 복구 불명은 자료를 보존하고 검토 또는 내보내기로 종료한다.
- 동기화 서비스의 폴더 이름만으로 파일시스템 종류를 추정하지 않는다. 지원할 저장 위치의 잠금·교체·동기화 동작을 실제로 확인한다. 다른 장치의 동시 변경이나 지원하지 않는 저장 환경에는 같은 보장을 표시하지 않는다.

현재 저장 코드는 [case_artifact_store.py](../../../src/ddk/services/case_artifact_store.py)에서 JSON을 직접 저장하고 [artifact_applier.py](../../../src/ddk/services/artifact_applier.py)에서 파일별 순차 쓰기를 한다. 이 사실은 새 계약이 이미 구현됐다는 증거가 아니다. 정적 확인 위치는 각각 18~57·124~134줄, 38~81줄이다.

### strict 후보의 정확한 계약

앱 작업은 `--network none`, 검사 작업은 `--network container:<app-id>`를 사용한다. 두 작업은 PID와 IPC를 공유하지 않는다. 파일 공유는 별도 명세하며 원본·기준·결과 폴더를 앱에 제공하지 않는다. 실행 전에 실제 설정을 검사하고 읽기·쓰기·외부 접속·자식 작업 종료의 실패 주입을 확인해야 한다. 이 방식은 Docker 문서상 구성 가능한 설계이며 이번 조사에서 실행하지 않았다. 지원 대상은 검증된 Linux 실행 작업이며 native Windows container의 동일 지원을 추정하지 않는다.

기준을 읽기 전용으로 전달하는 것과 기준이 사용자 요구를 정확히 나타내는 것은 다른 문제다. 승인된 기준·도구 판·대상 코드·자료 해시를 일치시켜야 한다. 앱의 화면과 사용 동작도 여전히 한정된 시험에서의 확인이며 모든 환경·사용자에 대한 정확성을 보증하지 않는다.

strict 환경이 없거나 설정을 확인하지 못하면 미지원으로 종료한다. trusted-local은 사용자가 승인한 저장소의 실행 위험을 수용한 별도 모드다. 이 모드에 strict와 같은 원본 외 자료 보호·실행 격리·기준 독립성 보장을 표시하지 않는다. 검사 전용은 모델 인증을 요구하지 않는 경로로 유지한다.

## 7. 현재 도구에 적용하지 않는 기준

현재 stdio 개발 도구에 사용자 계정·협업 서버·외부 DB를 추가하지 않는다. 다음은 현재 기능이 없으므로 설계 첫 범위에서 제외한다.

| 제외 사항 | 제외 근거와 다시 판단할 조건 |
|---|---|
| 제품 HTTP API의 CORS·CSRF·세션·다중 사용자 OAuth·RBAC | 현재 stdio 진입점과 개인 작업 폴더가 기준이다. 외부 HTTP MCP 또는 관리 서버를 제공하면 해당 인증·접속 보호를 다시 설계한다. 대상 앱의 미리보기 HTTP는 별도 실행 제한 대상이다. |
| 외부 DB의 복제·분산 트랜잭션·SQL 주입·운영 복구 | 현재 저장 계약은 사례 파일과 산출물이다. 대상 앱의 업무 DB 구조를 임의 생성하지 않는다. |
| 다중 사용자 SaaS의 사용량 결제·고객별 격리·99.99% 가용성 | 협업·원격 실행 요구와 실제 운영 지표가 생길 때 검토한다. 개인 검사 작업의 시간 제한·자원 상한은 제외하지 않는다. |
| 전체 WCAG 준수·ISO 인증·모든 브라우저와 장치의 동일 지원 | 부분 자동 검사의 범위와 공개 안내를 넘어서는 주장이다. 전체 기준·범위·독립 증거가 확보될 때 별도로 판단한다. |
| 별 10만·독점 기능·절대 안전·100점 | 이번 문서 검토와 공식 기능 설명으로 입증할 수 없다. |

이 제외는 개인정보 보호·지시 오염 방어·원본 보존·취소·내구성을 제외한다는 뜻이 아니다. 실제 제공하는 기능에 대응하는 S01~S32의 계약은 유지한다.
